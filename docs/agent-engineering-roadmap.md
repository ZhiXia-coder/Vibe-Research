# Vibe-Research 工程化 Agent 改造路线

> 目标：把现有的本地金融研究 Agent 升级为有业务闭环、可恢复、可观测、可评估、可治理的智能应用系统。本文只讨论系统工程，不构成投资建议。

## 1. 结论

Vibe-Research 已经不是“接一个模型、写几个 Prompt、调几个工具、做一个页面”的演示项目。它有明确的金融研究场景、六阶段业务流程、真实取数、确定性计算、证据链、Validator、合规 Gate、自动补跑、知识召回和多角色辩论。

它目前更准确的定位是：**具备强执行纪律和证据闭环的垂直研究 Agent**，但还不是完整的企业级 Agent 平台。主要短板在控制平面：没有数据库任务中心、用户与 RBAC、持久队列和重启恢复；高层任务计划仍是固定六阶段；多 Agent 主要服务于辩论；人工审批节点尚未形成正式状态机。

## 2. 六项能力审计

| 能力 | 已有能力 | 主要缺口 | 判断 |
|---|---|---|---|
| 业务闭环 | A 股/美股/港股研究场景；六阶段研究；报告、证据、计算、变化对比、知识归档 | 缺少按真实用户任务定义的长期业务 KPI 和产品化评测看板 | 基本满足 |
| 后端工程 | Node API、Bearer 鉴权、本地来源限制、日志追踪、子进程隔离、输入和路径安全 | 文件存储代替数据库；单本机 Token；无用户/租户/RBAC；无持久任务队列、并发配额和重启恢复 | 部分满足 |
| Agent 核心 | 阶段规划、工具调用、Validator、自动补跑、Gate 重写、多角色辩论 | 高层 Mission 仍是固定流水线；没有通用动态 DAG；多 Agent 不是通用协作执行器 | 较强但未完整 |
| 上下文工程 | 项目宪法、技能隔离、受控取数、知识召回、资料包、冲突裁决、上下文上限 | 缺少统一 Context Budget/选择理由的可视化和离线命中率评估 | 较强 |
| 可观测与评估 | `events.jsonl`、Manifest、Token usage、工具结果、耗时、Validator、硬测试和故障注入 | 原先缺少统一查询 API/界面；未配置模型价格表；缺少跨运行质量趋势 | 本轮已补第一版 |
| 人机协同 | 导入先生成草稿、用户可追问、运行需显式启动 | 无正式审批节点、暂停/恢复、人工修改留痕和审批权限 | 待建设 |

## 3. 本轮已完成：Agent 运行控制台

新增只读观测接口：

- `GET /observability/overview`：运行数、成功/失败、工具调用、工具失败和自动重试汇总。
- `GET /runs/:id/metrics`：Mission DAG、阶段、工具、恢复、耗时、模型、Token、质量代理指标。
- `GET /runs/:id/trace`：步骤 Trace 安全摘要。

桌面端新增“Agent 运行”页面，展示：

- 固定阶段 Mission DAG 和依赖关系；
- 每阶段状态、尝试次数和 Validator 结果；
- 命令/MCP 工具成功与失败；
- 自动重试、恢复成功、Gate 改写和失败事件；
- 总耗时、Token、Provider/模型、证据数、计算数和质量代理判定；
- 按步骤查看的 Trace 时间线。

安全边界：新接口不返回 Prompt、模型正文、完整命令输出、密钥或本机路径。没有模型价格配置时，成本明确返回 `not_configured`，不伪造估算。

## 4. 目标架构

```text
用户 / HR 可演示页面
        │
        ▼
API Gateway ── Auth / RBAC / Rate Limit / Audit
        │
        ▼
Mission Service ── PostgreSQL/SQLite（任务、步骤、审批、租户、幂等键）
        │
        ├── Planner：目标 → 动态 DAG → 风险/成本预算
        ├── Scheduler：优先级、并发配额、取消、超时、重启恢复
        └── Worker Pool
              ├── Research Agent
              ├── Evidence Agent
              ├── Risk/Critic Agent
              └── Report Agent
                       │
                       ▼
             Tool Gateway / Sandbox
                       │
                       ▼
           Validator / Recovery Policy

全链路旁路：Trace + Metrics + Cost + Eval + Human Approval
```

## 5. 后续实施顺序

### M2：持久任务中心与并发治理

- 引入 SQLite（本机版）并保留迁移到 PostgreSQL 的 Repository 接口。
- 建立 `missions`、`mission_steps`、`attempts`、`approvals`、`audit_logs` 表。
- API 不再直接 detached spawn；改为持久队列 + Worker。
- 支持幂等键、并发上限、取消、超时、进程退出回收和服务重启后的任务对账。
- 保留 `events.jsonl` 作为不可变审计账本，数据库只保存可查询索引和当前状态。

验收：服务运行中断后重启，排队任务不丢；运行中任务可被标记为 interrupted 并按策略恢复；并发量可配置且有测试。

### M3：动态 Mission DAG 与通用多 Agent

- Planner 根据用户目标、市场、数据可用性和成本预算生成 DAG，而不是只选择固定六阶段的子集。
- 每个节点声明输入、输出、工具权限、完成条件、重试策略和回滚/降级路径。
- 将多空辩论中的独立会话机制抽成通用 Role Agent Runtime。
- 增加 Verifier/Critic 节点；结果必须通过机器验证后才能进入下游。

验收：同一目标在数据缺失、工具失败和预算不足三种条件下生成不同但可解释的执行计划；失败路径可在控制台复盘。

### M4：身份权限、成本与评估

- 本机版至少提供 admin/researcher/viewer 三种角色；写操作和敏感 Trace 分权。
- 建立模型价格版本表，按每轮 usage 和价格生效时间计算真实成本。
- 建立跨运行 Eval 数据集：证据覆盖率、数字一致性、Validator 通过率、工具成功率、恢复率、时延和成本。
- 为关键指标设置基线和回归阈值，进入 CI。

验收：任何运行都能回答“谁发起、用了哪个模型、哪些工具、失败在哪、如何恢复、耗时和成本、质量是否达标”。

### M5：人机协同

- 在高成本、低置信度、证据冲突和最终归档前插入 Approval Node。
- 支持暂停、人工补充上下文、修改计划、批准/拒绝和恢复执行。
- 所有人工动作写入审计日志，保留修改前后版本。

验收：一次运行可在审批点暂停，服务重启后仍保持等待状态；批准后从原节点继续，不重复已完成且幂等的工具调用。

## 6. 面试叙事主线

推荐把项目讲成：从一个已有垂直研究 Agent 出发，先做代码级能力审计，再以可观测性为切入口建立 Mission/Trace/恢复/质量控制台，随后把直接子进程执行演进为持久任务中心和动态 DAG，最终加入 RBAC、评估和 HITL。

这条叙事能同时体现业务理解、TypeScript/React 工程、Agent 编排、上下文工程、可靠性、安全和评估体系；每个阶段都有可运行代码、接口、测试和可视化证据。
